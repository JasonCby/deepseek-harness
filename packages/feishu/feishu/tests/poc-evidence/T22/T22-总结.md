## 一、测试内容

### 1.1 进度表用例定义

**审批等待期间重启，24 小时后继续 → 原审批、任务、超时规则仍有效，无会话漂移。**

里程碑 S1-04 硬性要求：**必须真实跨 24 小时**，不能缩短时间替代。

### 1.2 本地架构里「什么能活下来」（执行前必须明确的真实行为）

测试设计和结论都基于当前代码的真实行为：

| 状态 | 重启后是否存活 | 机制 |
| --- | --- | --- |
| 会话上下文（完整对话历史） | ✅ 存活 | 会话事件持久化在 `$DSH_HOME/sessions/<项目目录>/<会话ID>/`（JSONL 分代文件） |
| 群聊 ↔ 会话路由 | ✅ 存活 | 会话 ID 由 `sha256(chatId#epoch)` 确定；epoch 持久化在 `$DSH_HOME/feishu-router-state.json`；重启后首条消息自动 `resume` 原会话 |
| 权限预设 / 审批策略覆盖 | ✅ 存活 | 以 `permission/preset`、`approval/policy` 事件记入会话日志，恢复时随日志重放 |
| **挂起中的审批（已提问未答复）** | ❌ **不存活** | 审批的 `approval/asked + approval/decided` 审计对必须包在一个已关闭的 turn 内；进程退出时未关闭的 turn 被视为「崩溃尾」，重载时丢弃（见 user-approval 模块的 `hasOpenTurn` 注释） |
| 业务超时规则（如「审批 24h 未处理自动关闭」） | ⚠️ 无原生实现 | Harness 侧没有业务超时引擎，属 POC 平台待补齐项 |

**结论**：T22 在本地要验证的是「会话 / 任务 / 权限状态跨重启 + 跨 24 小时不漂移」；「挂起审批本身存活」当前架构不支持，这本身就是 T22 的一个重要**实测发现**，如实记录为缺口，而不是绕过它。

`$DSH_HOME` 默认为 `C:\Users\<你>\.dsh`（可用环境变量 `DSH_HOME` 改）。

## 二、测试流程

### 前置准备

1. 确认凭据：`DSH_FEISHU_APP_ID` / `DSH_FEISHU_APP_SECRET` 已设置（公有云应用）。
2. 在 `deepseek-harness` 目录下启动：`pnpm dsh --profile web --patch apps/cli/config/examples/feishu-bot/cordis.yml`
3. 记录启动时间、进程 PID、工作目录。
4. 打开两个观察窗口（证据来源）：`$DSH_HOME\sessions\` 目录（会话文件）、`$DSH_HOME\feishu-router-state.json`（群聊 epoch，可能还不存在，发过 `/new` 才有）。

### 第 1 步（T0）：建立会话并埋下「记忆锚点」（约 10 分钟）

飞书向机器人发送（锚点每次执行前**重新随机生成**，勿复用）：

```text
请原样记住以下三个锚点，之后我会随时让你复述：
锚点A：QZ-8472-风筝
锚点B：58203197
锚点C：紫电-4096-灯塔-77
```

等机器人回复确认。再发一条制造「未完成任务」状态：

```text
把这次事件的处理步骤列成 3 条待办清单，先别执行，等我明天确认。编号用 TASK-2281、TASK-9054、TASK-3317。
```

**锚点设计原则**（重新生成时遵守）：

- **不可猜**：随机 4–8 位数字 + 随机词组合，避免顺序数字、常用口令——防止模型「蒙对」造成假阳性
- **字符级核对**：判定标准是逐字符一致，差一个字符即算漂移
- **可检索**：全文唯一字符串，便于在会话 JSONL 里 grep 验证事件真实存在
- **多类型**：纯数字（B）、字母+数字+中文（A）、中文+数字多段（C）各一，覆盖不同 tokenization
- **记录期望值**：生成后立刻填进证据模板，复测时逐项对照

立即记录基线证据：飞书聊天截图（两条消息 + 回复，带时间）；到 `$DSH_HOME\sessions\` 下找到新生成的会话目录（逐层进入项目目录，找 `feishu-` 开头的会话 ID 目录），记录完整会话 ID（形如 `feishu-<32位hex>`）和目录内文件列表、文件修改时间；若有 `feishu-router-state.json`，记录内容。

### 第 2 步（T0+10 分钟）：第一次重启

1. 完全结束 dsh 进程（Ctrl+C，确认进程退出）。记录停止时间。
2. 原命令重新启动。记录启动时间。
3. **验证点 R1 —— 上下文存活**：飞书发送「这次事件的三个锚点分别是什么？逐条原样复述。」
   - ✅ 通过标准：A/B/C 三条**逐字符一致** → 说明恢复的是原会话历史，不是新会话。
   - ❌ 若答不知道或任何字符不符 → 会话漂移，用例失败，保留证据。
4. **验证点 R2 —— 路由不漂移**：核对 `$DSH_HOME\sessions\` 下**没有新生成**的 `feishu-` 会话目录；原会话目录有文件更新（新事件追加了新分代文件）。会话 ID 与第 1 步记录一致。
5. **验证点 R3 —— 任务状态存活**：飞书发送「刚才让你列的待办清单呢？三条的编号和内容分别是什么？」
   - ✅ 通过标准：三个 TASK 编号与内容均正确（内容来自会话历史）。
6. 截图并记录全部结果。

### 第 3 步（T0+30 分钟内，可选但强烈建议）：挂起审批的重启行为实测

这一步产出 T22 的关键发现证据。需要一个能真正弹出审批的配置：把 overlay 的 `permissionPreset` 改成 `workspace-write`（approval: ask），并在浏览器打开 Web UI 中该群聊的会话（审批在 Web UI 应答）。

1. 飞书发送一条会触发写操作的请求（如「在当前目录创建一个 note.txt 写上今日小结」）。
2. Web UI 弹出审批请求后，**不要点**，直接结束 dsh 进程。
3. 重启，飞书追问「刚才的文件建了吗？」
4. 记录实际行为（预期：挂起的审批随进程消失，agent 不会继续原审批动作，可能需要重新发起）——**这就是「挂起审批不存活重启」的缺口证据**，注明这是当前架构设计（崩溃尾丢弃），非测试失误。
5. 测完把 `permissionPreset` 改回 `read-only`。

### 第 4 步：保持运行，等待 24 小时

- 进程保持运行或再次停掉均可（建议保持运行，更贴近生产形态；若想覆盖「关停 24h」形态，可停进程，24h 后再启动）。
- **记录准确的 T0 时间与计划复测时间**，定好闹钟。期间正常做 T25/T26/T16，但**不要在这个测试群里发 `/new`**（会 bump epoch 开新会话，测试作废）。

### 第 5 步（T0+24h 后）：到期验证

重复第 2 步的全部验证点（R1 代号、R2 会话 ID 不变、R3 待办清单），外加：

- **验证点 R4 —— 连续可用性**：发一条新任务（如「在清单上加一条：复核证据」），确认正常响应、无报错、无重复投递。
- **验证点 R5 —— 超时规则**：本地无业务超时引擎，此项记「平台待补齐」；若第 3 步做过审批挂起实测，把其行为结论一并写入。

## 五、常见坑（执行经验沉淀）

- **误发 `/new`**：任何参与测试的群成员发 `/new`、`/reset`、`/新会话` 都会重置会话，24h 计时作废。
- **Web UI 占用会话**：Web UI 打开同一会话时持有写锁；飞书侧会自动「借用」该活 agent，不会报错，但测「重启恢复」时要确保进程是整个重启的。
- **改 `workspacePath`**：会话按工作目录分项目存储，中途改 overlay 的 `workspacePath` 会找不到旧会话。
- **进程没退干净**：Windows 下确认 node 进程完全退出再启动，否则不算真重启。
- **回填进度表**：状态改为「已完成」时，负责人、实际完成日期、证据执行包链接三者缺一不可，否则不计有效通过。
