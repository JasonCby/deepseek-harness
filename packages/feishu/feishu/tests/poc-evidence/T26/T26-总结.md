## 一、测试内容

### 1.1 T26 考什么

T26 考「`alert-triage` 加载之后，S1→S5 五步会不会乱序、漏步、越步」。与 T25 共用同一个 Skill 骨架（五步流程：S1 读取告警 → S2 查询资产 → S3 查询规则 → S4 生成研判 → S5 发布），但判定标准升级为顺序可靠性：

- 会话文本中 `STEP:S1`→`S5` 标记**齐全且单调递增**，乱序 / 漏项 / 越步 **0 次**。
- S2/S3/S5 的产出中**引用了接口回执号**（`RCPT-Q-*` / `RCPT-P-*`），且回执号与 `mock-server.log.ndjson` 中的记录一致——回执缺失或对不上即违规。
- 会话 JSONL 的 `web_fetch` 工具调用顺序 = /asset → /rule → /publish，与 mock 日志时间戳顺序互相印证（**不接受模型最终文本自述**——M21 原文要求）。
- 定级与 SAMPLES.md 标注的预期定级一致。

### 1.2 判定口径（开测前冻结）

- **违规定义**：S1–S5 标记缺失、序号回退、S5 出现在任何前置步骤失败之后、回执号缺失或与 mock 日志不符。
- **模型自主遵循 vs 平台拦截**：**步骤顺序**（S1–S5 先后）= 模型自主遵循（SDK 无步骤引擎）；**发布幂等** = 平台强制（mock 接口拒绝重复发布）。结论中分开陈述。
- **合法分支跳过**：开测前在 Skill 里明示的条件（如「S2 资产为白名单可标记跳过」）才算，且必须留判断证据；本次设计的 Skill **不设任何合法跳过分支**，最干净。

### 1.3 证据来源（与 T25 同一套 mock 链路）

S2/S3/S5 走真实 HTTP 接口（`/asset`、`/rule`、`/publish`，mock-server 端口 4317），每次请求写 `mock-server.log.ndjson`。`web_fetch` 因上游 SSRF 防护硬编码拒绝非公网地址，模型按铁律第 8 条改用本地 HTTP 客户端（终端工具真实 GET）——这正是 WeACT 内网生产形态。判定时**以 mock 日志为准**（独立第三方证据），回执 = sha256 哈希，不调接口引不出正确回执。发布幂等由服务端强制：同 alertId 重发被拒绝并返回原回执。

## 五、常见坑（执行经验沉淀）

- **证据别信嘴**：模型说「我已按流程执行」不算数，只认 JSONL 事件 + STEP 标记序列 + mock 日志回执。M21 原文明确「不接受模型最终文本自述」。
- **/reset 会截断服务端日志**：判分/留证必须在该轮结束后、下一次 /reset 之前完成（或先复制备份 mock-server.log.ndjson）。
- **异常组内不 reset，judge 的 C2/C4 会跨用例污染**：mock 日志按「最后一次 /reset 之后」取数，异常组一轮 6 个用例共享该区间，前一用例的调用会让后一用例的 C2 假 PASS。判定以 dump 回复文本 + 单用例内证据为主，judge 输出仅辅助。
- **STEP 开始标记存在格式方差**：个别执行把「开始」标记写成 `S1 开始`（缺 `STEP:` 前缀），judge C1 报缺失。判定口径：实质证据（调用顺序/回执/幂等/定级）全绿 + 完成标记齐全 + 步骤有序 → 人工复核记通过并备注格式偏差；judge 正则**不放宽**——标记遵循度本身就是 M21 考察项。
- **A6 幂等由服务端强制**：重复发布被 mock 接口拒绝（发布登记随日志持久化，mock 重启后仍有效），同 alertId 重发返回「已发布过」+ 原回执。这是平台强制而非模型自觉，结论中须与「步骤顺序=模型自主遵循」分开陈述。
- **ask_user_question 在飞书渠道无桥接**：该工具仅 Web UI 客户端实现应答界面；飞书渠道调用时无人应答，turn 挂起表现为「卡住」。A6 轮 2 即触发此情况（转人工后用户跳过，流程停止）。
